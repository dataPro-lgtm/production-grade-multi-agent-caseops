# ADR-0010：正式发布必须是一条可验证的证据链

- 状态：Accepted
- 日期：2026-07-27
- 决策者：CaseOps maintainers

## 背景

测试通过只能说明某次执行满足了测试断言，不能回答消费者真正关心的四个问题：下载物来自哪个提交、构建时装入了什么、交付物是否被替换、第三方能否独立复现和验证。

多 Agent 系统还会放大这个问题。它同时包含业务状态、Agent 协议、工具权限、知识证据、评测基线与运行恢复。如果发布只上传源码压缩包，读者无法判断运行中的镜像是否仍然对应已经验收的版本。

## 决策

1. v1.0 发布只从精确 SemVer 标签触发；标签版本必须与 Python 包和服务版本一致。
2. 运行时与开发依赖分别由带哈希的锁文件固定，Python 基础镜像固定到不可变 digest。
3. 干净环境验收只使用 `git archive HEAD`，不得读取工作区中的 `.env`、数据库、缓存或历史证据。
4. 干净源码必须重新构建镜像，并验证非 root 用户、OCI 版本标签、源码提交和运行时包版本。
5. 发布证据清单同时绑定 Git commit、镜像 digest、数据库迁移头、OpenAPI、系统评测、GameDay 和 SPDX SBOM。
6. GitHub Actions 对镜像生成来源证明和 SBOM 证明，对下载包生成来源证明；消费者必须主动验证证明和校验和。
7. 来源证明不等于安全证明。发布说明必须保留部署身份、TLS、密钥管理和威胁建模等已知边界。

## 结果

优点：

- 发布结论从维护者声明变成第三方可重复执行的验证步骤；
- 下载包、容器镜像、源码提交和验收证据形成同一身份链；
- 依赖与基础镜像不会在相同标签下静默漂移；
- 失败的发布门禁不会创建 GitHub Release。

代价：

- 锁文件、SBOM、证明与发布工作流都需要持续维护；
- 发布耗时明显高于普通 CI；
- 依赖更新必须显式重建锁文件并接受安全与回归检查。

## 未选择的方案

### 仅依赖 GitHub 自动生成的源码压缩包

拒绝。它没有绑定运行镜像、运行依赖、数据库迁移和系统验收证据。

### 只签名一个 `latest` 镜像标签

拒绝。标签可以移动，不能作为稳定身份；运行和验证必须落到 digest。

### 把 SBOM 当成漏洞扫描报告

拒绝。SBOM 是组件清单，不是安全结论；来源证明也只证明构建身份，不证明代码安全。
