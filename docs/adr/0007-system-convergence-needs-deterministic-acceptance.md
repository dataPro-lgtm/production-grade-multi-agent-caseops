# ADR-0007：系统合龙使用确定性验收与运行时来源图

- 状态：Accepted
- 日期：2026-07-27

## 背景

Slice 3 已有多专业协作，Slice 4 已有受治理的 Context Pack。两条链分别正确，不等于系统结论正确：它们可能使用不同规则版本、对材料状态得出相反判断，或对人工复核门禁理解不一致。

让一个更大的模型读取两份自然语言总结并再次总结，无法证明冲突被发现，也无法说明最终主张来自哪里。

## 决策

1. Central Supervisor 只持有目标、已验证 DAG、父子运行引用和系统终态；
2. Context Team 与 Collaboration Team 分别持有自己的状态、验收和 Artifact；
3. 系统级 Reducer 用确定性规则核对关键业务不变量，不由模型决定是否通过；
4. 所有最终 Claim 必须保留证据引用；
5. Runtime Context Graph 连接 Goal、Plan、Step、Task、Artifact、Claim、Evidence、Acceptance 与 Result；
6. 图只保存元数据、稳定引用、分类和摘要，不复制原始 Prompt 与业务载荷；
7. Trace、知识图谱和 Runtime Context Graph 各自保留独立职责。

## 结果

优点：

- 冲突会成为失败状态，不会被语言润色掩盖；
- 父子团队可以独立演进，系统只依赖版本化 Artifact；
- 审计者能从最终主张反向定位证据与责任主体；
- 幂等重放不会重复创建系统运行和来源图。

代价：

- 需要维护跨团队字段映射与版本兼容；
- 来源图增加持久化和清理策略；
- 新增业务主张时必须同步增加验收规则和回归样例。

## 不采用的方案

- 单一“超级 Supervisor”：状态、权限、失败域和上下文会重新耦合；
- 仅依赖分布式 Trace：Trace 能说明调用发生过，不能证明主张受什么证据支持；
- 仅依赖知识图谱：知识图谱表达领域事实，不拥有一次运行的计划、责任和验收状态；
- 使用模型做最终冲突消解：模型可以辅助解释，但不能持有系统通过权。
